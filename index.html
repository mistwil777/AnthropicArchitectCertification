Module 1 — Conception de plateformes et de solutions Claude

Les 4 décisions architecturales

Concevoir une solution Claude = répondre à 4 questions dans cet ordre. Chaque décision contraint la suivante.

flowchart LR D1["1 - Decomposition"] D2["2 - Pattern"] D3["3 - Architecture"] D4["4 - Modele + Entree"] D1 --> D2 --> D3 --> D4 style D1 fill:#1c1f2e,stroke:#4f8ef7,color:#ddd8f0 style D2 fill:#1c1f2e,stroke:#a78bfa,color:#ddd8f0 style D3 fill:#1c1f2e,stroke:#2dd4a0,color:#ddd8f0 style D4 fill:#1c1f2e,stroke:#fbbf24,color:#ddd8f0

Exemple fil rouge : assistant de traitement de sinistres d'assurance.

  • D1 : Claude lit + rédige / SQL vérifie la couverture / Humain valide > 5 000 £
  • D2 : Workflow (étapes connues à l'avance, coût d'erreur élevé)
  • D3 : RAG sur les polices d'assurance
  • D4 : claude-sonnet, context window compressée, API directe
Règle
Séquence obligatoire. Sauter D1 pour aller à D4 = optimiser la latence d'un système mal décomposé.

Règle
Piège exam : lookup de données existantes (garantie, stock, tier, politique publiée) → Système existant, même si ça ressemble à du jugement.
Situation réelle
Règle sinistre > £5 000 confiée à Claude : - 14 000 sinistres → 41 mal routés ("environ cinq mille livres" ≠ seuil déclencheur) - Dérive silencieuse — détectée à l'audit, pas par le système - Cause : règle déterministe confiée à un système probabiliste
cliquer pour répondre
"Vérifier si la garantie s'applique à ce numéro de série" → qui ?
réponse
Système existant — lookup en base, pas un jugement.
cliquer pour répondre
"Émettre le remboursement" → qui ?
réponse
Humain — action financière irréversible, même si l'éligibilité est automatique.
cliquer pour répondre
Règle déterministe (ex : seuil £5 000) → erreur de décomposition ?
réponse
La confier à Claude. Les seuils exacts doivent aller au Système existant — Claude est probabiliste.
cliquer pour répondre
Claude + outil externe = quel pattern minimum ?
réponse
Augmented LLM — un appel + tool/RAG. Pas encore un Workflow.

Les 3 patterns

Arbre de décision — quel pattern choisir ?

flowchart TD Q1{Etapes previsibles ?} -- Non --> AG[Agent] Q1 -- Oui --> Q2{Cout erreur eleve ?} Q2 -- Oui --> WF[Workflow] Q2 -- Non --> Q3{Observabilite requise ?} Q3 -- Oui --> WF2[Workflow] Q3 -- Non --> Q4{Latence ou tokens critiques ?} Q4 -- Oui --> AL[Augmented LLM] Q4 -- Non --> WF3[Workflow] style AG fill:#1c1f2e,stroke:#a78bfa,color:#ddd8f0 style WF fill:#1c1f2e,stroke:#2dd4a0,color:#ddd8f0 style WF2 fill:#1c1f2e,stroke:#2dd4a0,color:#ddd8f0 style WF3 fill:#1c1f2e,stroke:#2dd4a0,color:#ddd8f0 style AL fill:#1c1f2e,stroke:#4f8ef7,color:#ddd8f0
Règle

Les 4 sous-patterns du Workflow

flowchart TB subgraph Chaining direction LR c1[Extraire] --> c2[Classifier] --> c3[Synthétiser] end subgraph Routing direction LR r0[Input] --> r1{Type ?} r1 -->|Billing| r2[Agent billing] r1 -->|Tech| r3[Doc tech] r1 -->|Escalade| r4[Humain] end subgraph Parallelization direction LR p1[Contrat 1] --> p4[Synthese] p2[Contrat 2] --> p4 p3[Contrat N] --> p4 end subgraph EvaluatorOptimizer direction LR e1[Generer] --> e2{OK ?} e2 -->|Non| e1 e2 -->|Oui| e3[Output] end
cliquer pour répondre
Quand utiliser Evaluator-Optimizer plutôt que Chaining ?
réponse
Quand la qualité est vérifiable mais une seule tentative n'est pas fiable. Ex : code + suite de tests.
cliquer pour répondre
Agent vs Workflow — différence fondamentale ?
réponse
Flux de contrôle — Workflow : votre code. Agent : le modèle. L'agent échoue silencieusement, le Workflow avec une erreur déboguable.
cliquer pour répondre
Evaluator-Optimizer — quand le préférer à un simple Chaining ?
réponse
Quand la qualité est vérifiable objectivement (tests, critères) et qu'une seule passe est insuffisante.
cliquer pour répondre
Fine-tuning — quand est-ce justifié selon Anthropic ?
réponse
En dernier recours — après avoir épuisé prompting, tools et Workflows. Disponibilité limitée sur Claude.

Récupérabilité des défaillances

flowchart LR F1[Sub-agent echoue] -- Recuperable --> A1[Relancer ou Rediriger] F2[Orchestrator echoue] -- Irrecuperable --> A2[Execution perdue] style F1 fill:#1c1f2e,stroke:#fbbf24,color:#ddd8f0 style F2 fill:#1c1f2e,stroke:#f87171,color:#ddd8f0 style A1 fill:#1c1f2e,stroke:#2dd4a0,color:#ddd8f0 style A2 fill:#1c1f2e,stroke:#f87171,color:#ddd8f0
Règle
Contrôle de couverture : résultats reçus == unités envoyées. Signaler l'écart avant synthèse.
Situation réelle
Audit contractuel — 50 sections, 2 unités tombées : - Orchestrator synthétise "48 sections examinées" sans contrôle de couverture - Résumé fluide et confiant → personne ne détecte les 2 manquantes - Transmis au responsable juridique comme complet
cliquer pour répondre
Asymétrie Orchestrator vs Sub-agent — laquelle est récupérable ?
réponse
Sub-agent (relancer). Orchestrator : souvent irrécupérable — il détient l'objectif et la synthèse.
cliquer pour répondre
Pourquoi un résumé fluide est dangereux dans un Fan-out ?
réponse
Il masque les unités manquantes. La confiance apparente empêche de détecter les défaillances silencieuses.
cliquer pour répondre
Contrôle de couverture Fan-out — quand l'effectuer ?
réponse
Avant la synthèse — vérifier que résultats reçus == unités envoyées. Sinon signaler l'écart.
cliquer pour répondre
Orchestrator vs Sub-agent — qui détient l'objectif global ?
réponse
L'Orchestrator — sa défaillance est donc souvent irrécupérable contrairement à un sub-agent.
